# MEETING-TRANSCRIPT-QUALITY-AUDIT — 2026-08-07

> Многоагентный аудит (14 агентов, ultracode): почему транскрипты созвонов грязнее, чем у конкурентов.
> Все цифры — из тулов этой сессии (2026-08-07). Реальные данные: suspect-transcripts.log (1281 записей) + 114 финальных транскриптов июль-август из MetaWhisp.store.

## Замеренная реальность (Confirmed)

- Старый мусор (YouTube-фразы «Продолжение следует», DimaTorzok) отфильтрован на ~98% — 16 утечек против 942 пойманных за июль-август. Эта война выиграна.
- Доминирующая грязь СЕГОДНЯ, фильтров на неё НЕТ вообще:
  1. **863 кросс-канальных дубля** (одна фраза и как Me:, и как Them:) в 66/114 митингов — эхо динамиков в микрофон + нулевой дедуп в DualStreamMerger.
  2. **410 повторных петель** (слово 3+ раз подряд) в 82/114 митингов — repetition-фильтр заперт за RMS<0.003 целого 5-минутного чанка, на чанках с речью не срабатывает никогда.
  3. **2-5 иноязычных фрагментов** (испанский/польский мусор в русском митинге) в каждом свежем транскрипте — язык автоопределяется на каждый чанк каждого канала независимо.
- Итоговое соотношение: ~1.4 события мусора ДОХОДИТ до финального транскрипта на каждое пойманное.

## Подтверждённые причины (6, после адверсариальной проверки)

### 1. [MAJOR] No acoustic echo cancellation on mic path — speaker bleed puts "Them" speech into the "Me" channel, transcribed twice at far-field quality

**Где:** `Services/Audio/AudioRecordingService.swift:159`

**Механизм:** The mic is captured via a raw `engine.inputNode` tap with no voice processing. `grep -rn setVoiceProcessingEnabled|voiceProcessing|echoCancel` across the repo returns zero hits — there is no AEC anywhere. SystemAudioCaptureService only excludes MetaWhisp's OWN audio from the system capture (SystemAudioCaptureService.swift:160 `config.excludesCurrentProcessAudio = true`); nothing removes the meeting's remote audio from the MIC. Any user on built-in speakers (no headphones) has every word the other side says re-enter the mic as reverberant, low-SNR room audio. The dual-pass design then transcribes that copy as the "Me" channel: the same speech appears twice in the merged transcript (once as Them, once garbled as Me), and far-field reverberant audio is a canonical Whisper hallucination trigger (repeated single words, junk fragments). Competitors using voice-processing I/O (Apple AEC) do not have this failure mode.

**Вердикт проверки:** Confirmed by tracing the real call path. (1) AudioRecordingService.swift:159/185 captures the meeting mic via a raw engine.inputNode tap; repo-wide grep for setVoiceProcessingEnabled/voiceProcessing/echoCancel/AUVoiceProcessingIO returns zero hits — no AEC exists anywhere. (2) MeetingRecorder.swift:53/92/189-195 confirms this service IS the meeting "Me" channel, kept separate for dual-pass diarization (stop() at :268-296). (3) SystemAudioCaptureService excludes only MetaWhisp's own process audio (excludesCurrentProcessAudio = true); nothing removes remote-meeting playback from the mic signal, so on speakers every remote word re-enters the mic as reverberant far-field audio. (4) No downstream guard neutralizes it before the final transcript: the chunk-skip gate is rms < 0.0005 (AppDelegate.swift:1879), far below audible bleed; the hallucination pattern filter only runs when rms < 0.003 (AppDelegate.swift:1925), so typical bleed loudness BYPASSES it while the bleed itself (long silence + faint reverberant speech on a listening-heavy mic channel) is the canonical Whisper trigger for exactly the reported garbage (repeated words, «Продолжение следует», junk fragments); DualStreamMerger.mergeStreams (DualStreamMerger.swift:24-26) is a plain timestamp sort with zero cross-channel dedup, and renderTranscript emits every segment, so garbled "Me:" duplicates of "Them:" speech land verbatim in the saved transcript (AppDelegate.swift:1842→1800). (5) The confidence gate (AppDelegate.swift:1983) drops only low-confidence utterances, not confidently-decoded duplicated speech. The fix would change user-visible output: AEC removes the bleed signal at the source, eliminating both the duplication and the hallucination substrate. Impact is conditional on no-headphones use (headphone users unaffected; "Them" channel always clean), hence major rather than critical.

**Фикс (с поправками верификатора):** setVoiceProcessingEnabled(true) alone is insufficient/risky on macOS: AUVoiceProcessingIO by default DUCKS other applications' audio — i.e. it would attenuate the very Zoom/Meet playback the user is listening to. The fix must also set inputNode.voiceProcessingOtherAudioDuckingConfiguration (macOS 14+) with enableAdvancedDucking=false / duckingLevel=.min, and must re-read inputNode.outputFormat(forBus: 0) AFTER enabling voice processing (the hardware format changes when VP is enabled) before creating the AVAudioConverter at AudioRecordingService.swift:177. Also verify the AVAudioEngine output node is attached/rendering as required for the VP unit's echo reference, and gate the whole thing to the meeting path (dictation doesn't need AEC and VP adds latency/CPU).

### 2. [MAJOR] Silence guard compares raw-RMS threshold against sqrt-boosted level — silence auto-stop and calendar-end stop effectively never fire, so post-call ambience/silence tails get recorded and transcribed into the exact reported junk

**Где:** `Services/Audio/MeetingRecorder.swift:331`

**Механизм:** Units mismatch. `silenceRMSThreshold = 0.025` (MeetingRecorder.swift:74) is documented as a raw RMS calibration ("below normal speech (~0.05+)"), but it is compared (line 331) against `audioLevel`, which is NOT raw RMS: both sources publish the boosted UI level `sqrtf(min(rms*12, 1))` (AudioRecordingService.swift:291, SystemAudioCaptureService.swift:242), merged by max (MeetingRecorder.swift:108-112). Boosted 0.025 corresponds to raw RMS 5.2e-5 (0.025²/12) — near digital zero. A typical mic noise floor (raw ~1e-3 → boosted ~0.11) never drops below it, so `silentSince` never arms. Consequences: (a) the 3-minute silence auto-stop (AppSettings.swift:117 default 3) never fires; (b) `hasBeenContinuouslyQuiet` (MeetingRecorder.swift:376-379) is永 false → `recentAudioActive` is always true at AppDelegate.swift:2613 → the calendar-end stop is vetoed (silentExtend), so recording continues past the meeting up to the 240-min cap (AppSettings.swift:108). Hours of post-call room tone / whatever plays on the Mac land in the meeting buffers. Downstream, those chunks pass the gate (skipped only if raw chunk RMS < 0.0005, AppDelegate.swift:1879) and reach Whisper, whose canonical output on Russian near-silence is exactly «Продолжение следует...», «Субтитры сделал DimaTorzok», «Спасибо за просмотр» — the strings users are reporting; the blocklist filters (AppDelegate.swift:1920-1929) only catch known phrases.

**Вердикт проверки:** CONFIRMED by tracing the real call path. (1) Units mismatch verified: silenceRMSThreshold=0.025 (MeetingRecorder.swift:74, comment calibrates it in raw-RMS terms "below normal speech ~0.05+") is compared at line 330-331 against audioLevel, which is the sqrt-boosted UI level sqrtf(min(rms*12,1)) from BOTH sources (AudioRecordingService.swift:291, SystemAudioCaptureService.swift:242), merged by max (MeetingRecorder.swift:108-112). Boosted 0.025 = raw RMS 5.2e-5 (~-86 dBFS), below any live mic noise floor, so silentSince (sole writer: the guard sink, verified by grep) effectively never arms. In-code history corroborates the boosted-as-RMS confusion: CalendarEndStopDecision.swift:97-101 logs "RMS 0.099-1.0" — only possible in boosted space. (2) Calendar-end consequence verified structurally: hasBeenContinuouslyQuiet always false (MeetingRecorder.swift:376-379) → recentAudioActive always true (AppDelegate.swift:2613) → .stopNow blocked (CalendarEndStopDecision.swift:120 requires !recentAudioActive) AND .hardStop blocked (line 103) → only 3 notify cards then infinite silentExtend; auto-stop is impossible until the 240-min cap (AppSettings.swift:108). (3) The finding is UNDERSTATED: window-loss call-end detection deliberately does NOT stop recording ("recording untouched — silence guard owns stop", AppDelegate.swift:1440-1470), so the broken guard is the DESIGNATED stop authority for auto-started recordings; same units bug also kills the post-start empty-room sniff (AppDelegate.swift:2545, audioLevel<0.01 ⇒ raw 8.3e-6) and the calendar probe's instantaneous check (boosted audioLevel passed as audioRMSLastNSec vs raw-calibrated 0.005, AppDelegate.swift:2612-2618). (4) Downstream does NOT fully neutralize: chunk gate only skips raw RMS<0.0005 (AppDelegate.swift:1879) — room tone ~1e-3 passes to Whisper; known-phrase strip catches the canonical strings per-utterance, but repetition/junk detection only runs at chunk RMS<0.003 (line 1925), unknown hallucination variants pass, and real post-call audio (music/videos via system channel) is transcribed into the meeting with no possible filter. Fix would visibly change output (recording ends near actual meeting end, junk tail disappears). Severity capped at major, not critical: applies only to auto-started recordings (manual mode disables guards by design, MeetingRecorder.swift:210 / AppDelegate.swift:1493), explains post-call TAIL garbage rather than mid-meeting junk, and the exact reported phrases are substantially stripped by the 2026-05-28 finalize-path filters — the surviving user impact is unstripped hallucination variants, junk at RMS≥0.003, irrelevant post-call content, wasted quota, and 4-hour zombie recordings.

**Фикс (с поправками верификатора):** Fix all THREE consumers of boosted audioLevel misused as raw RMS, not just the silence guard: (1) MeetingRecorder.swift:331 silence guard vs silenceRMSThreshold; (2) AppDelegate.swift:2545 post-start empty-room sniff (audioLevel < 0.01); (3) AppDelegate.swift:2612-2618 calendar-end probe passing audioLevel as audioRMSLastNSec against CalendarEndStopDecisionRules.defaultQuietRMSThreshold=0.005 (CalendarEndStopDecision.swift:42). Cleanest: publish a raw-RMS value alongside the boosted UI level in AudioRecordingService/SystemAudioCaptureService, have MeetingRecorder track max(rawMic, rawSys) for guards, keep boosted strictly for UI bars/waveform. Re-derive thresholds empirically (log raw RMS during a real call + post-call tail) rather than trusting the 0.025/0.005 comments — they were written against the wrong unit. Add unit tests pinning: (a) speech-level raw RMS does not arm silentSince, (b) room-tone raw RMS does arm it, (c) CalendarEndStopDecision reaches .stopNow when the room is genuinely quiet.

### 3. [MAJOR] Idle-channel chunks (Me silent while Them speaks) are transcribed with the repetition/hallucination filter bypassed — RMS gates at 300-second granularity

**Где:** `App/AppDelegate.swift:1925`

**Механизм:** Dual-pass diarization guarantees that for most of a meeting one channel contains near-silence (breathing, keyboard, room noise, speaker bleed) while the other has speech. A chunk is only skipped when chunk.count < 8000 samples or whole-chunk RMS < 0.0005 (~-66 dBFS) (AppDelegate.swift:1879) — ambient mic noise is typically 0.001-0.01, so 5-minute noise-only chunks ARE sent to Whisper, which is the textbook generator of «Продолжение следует…», «Субтитры сделал», credits, and repeated words. The only content-based hallucination check, isHallucination() with containsExcessivePhraseRepetition(), runs ONLY when whole-chunk RMS < 0.003 (AppDelegate.swift:1925). So any chunk between RMS 0.003 and real speech level — faint bleed, typing, fan — gets zero repetition filtering. And because RMS is computed over the entire 300s chunk (AppDelegate.swift:1875), 10s of real speech + 290s of silence produces a 'loud' chunk: Whisper hallucinates across the 290 silent seconds and everything except the regex-strippable phrases is kept. trimSilenceEdges (AppDelegate.swift:2077-2100) only removes leading/trailing silence, never internal stretches — including the hard-zeroed dictation pause windows injected by MeetingRecorder.applyPauseMutes (MeetingRecorder.swift:250-261), which give Whisper long internal digital silence mid-chunk.

**Вердикт проверки:** Core mechanism verified in code: AppDelegate.swift:1879 skips chunks only below RMS 0.0005/8000 samples; :1925 gates the text-based isHallucination + containsExcessivePhraseRepetition (TranscriptionCoordinator.swift:789) on WHOLE-chunk RMS < 0.003 computed at :1875 over up to 300s; trimSilenceEdges (:2077-2100) is edge-only so internal silence — including hard-zeroed pause windows from MeetingRecorder.applyPauseMutes (MeetingRecorder.swift:250-261) — reaches Whisper mid-chunk. A 300s chunk with 10s of speech has whole-chunk RMS ≈ 0.009 > 0.003, so text-level repetition/hallucination filtering is bypassed for the entire chunk, and DualStreamMerger applies no filtering before the final transcript. HOWEVER the finding's claim of 'no per-utterance check' is wrong: AppDelegate.swift:1983 applies TranscriptionConfidenceGate per utterance with repetition (compression>2.4 AND logProb<-0.5) and silence (noSpeech>0.5 AND logProb<-1.0) branches, with metrics populated by both Groq verbose_json (CloudWhisperEngine.swift:245-253) and WhisperKit (WhisperKitEngine.swift:134-141); stripHallucinationTokens also runs per utterance regardless of RMS, removing the named artifacts (DimaTorzok, «Продолжение следует», «Субтитры…»); WhisperKit additionally dedups consecutive duplicate segments engine-side (WhisperKitEngine.swift:109-119). These partial guards reduce but do not close the gap: the gate is deliberately precision-first, its silence branch is inert on-device (noSpeechProb hardcoded 0), confident hallucination loops (logProb ≥ -0.5) and novel unlisted junk phrases pass, and the cloud Groq path lacks WhisperKit's engine-level dedup. Residual garbage from mixed speech+silence idle-channel chunks demonstrably reaches the final user-visible transcript, so the finding is real but its severity is overstated.

**Фикс (с поправками верификатора):** The proposed fix should be scoped as an EXTENSION of the existing per-utterance pass at AppDelegate.swift:1976-2003, not as introducing a missing layer: a per-utterance confidence gate already runs at :1983 (TranscriptionConfidenceGate — repetition and silence branches on Whisper decode metrics). The actual gap is that the TEXT-based checks (containsExcessivePhraseRepetition / isHallucination) are gated on whole-chunk RMS at :1925. Correct fix: compute RMS over each utterance's own sample window (leadOffsetSamples + w.start*16000 ..< w.end*16000 within the trimmed chunk) and apply isHallucination/containsExcessivePhraseRepetition per utterance when that window is quiet, keeping the whole-chunk check as-is. Highest-value target is the cloud Groq path (CloudWhisperEngine has no engine-level dedup/cleanup, unlike WhisperKitEngine.swift:94-119); also note the silence branch of the confidence gate is inert on-device because WhisperKit hardcodes noSpeechProb=0, so the text-based per-utterance check is the only silence defense there. Full VAD segmentation inside the chunk is heavier than needed.

### 4. [MAJOR] Meeting per-utterance path has zero pattern/repetition/energy checks — the entire isHallucination library is gated on whole-chunk RMS (<0.003 over a ~5-min chunk) and is unreachable whenever the chunk contains ANY speech

**Где:** `App/AppDelegate.swift:1925`

**Механизм:** transcribeStreamChunked computes one RMS per ~300s chunk (line 1875, AFTER trimSilenceEdges which raises RMS by cutting quiet edges). isHallucination — which holds ALL exact patterns («музыка», «субтитры», bare «subscribe», «продолжение следует», «thank you for watching») AND containsExcessivePhraseRepetition — only runs when chunk RMS < 0.003 (line 1925). The Them/system channel is line-level loud, and any Me chunk where the user spoke even briefly exceeds 0.003. Inside a loud chunk, each utterance (lines 1976-2003) gets ONLY: confidence gate (1983) + stripHallucinationTokens (1988). Strip's regex list (TranscriptionCoordinator.swift:606-648) does NOT cover: bare 'Thank you.'/«Спасибо.» loops, «(ДИНАМИЧНАЯ) МУЗЫКА»/caption artifacts, arbitrary word loops («и и и и», «Прошу, да» x4, «Дум-дум-дум»), CJK/Hangul junk (mixed-script check is chunk-level only, TranscriptionCoordinator.swift:691), or 'thank you for watching' (strip regex `thanks?\s+for\s+watching` at line 640 doesn't match the 'thank you' variant). All of these land verbatim in the final Me:/Them: transcript.

**Вердикт проверки:** Confirmed end-to-end with production data. (1) Code path is exactly as described: AppDelegate.swift:1875 computes one RMS per ~300s trimmed chunk; :1925 gates isHallucination (whole exact-pattern library + containsExcessivePhraseRepetition, TranscriptionCoordinator.swift:711/785) on chunk RMS<0.003; the per-utterance loop (:1976-2003) applies only the precision-first confidence gate (:1983, nil-metrics→keep, WhisperKit noSpeechProb hardcoded 0) and stripHallucinationTokens (:1988), whose patterns (Services/System/TranscriptionCoordinator.swift:606-648) cover none of the claimed classes — verified line 640 `thanks?\s+for\s+watching` does not match "thank you for watching", no bare Thank-you/Спасибо-loop, no МУЗЫКА/caption class, no word-loop handling; mixed-script check needs 3+ scripts and is chunk-level only (:691). (2) No downstream guard: DualStreamMerger.renderTranscript does zero filtering; persistMeetingTranscript→HistoryService.save stores verbatim; no LLM polish. (3) Decisive: the FINAL saved transcripts in ~/Library/Application Support/MetaWhisp.store contain the garbage — 111/395 meeting transcripts hit at least one class; "Thank you. Thank you. Thank you" ×18 (latest 2026-07-07, after both the 2026-05-28 strip expansion and the confidence gate live by 2026-06-12), МУЗЫКА-class ×10 (latest 2026-07-14), «и и и и» loops ×4 (latest 2026-07-21), «Спасибо.» loops ×2 — all inside Me:/Them: lines surrounded by real speech, i.e. loud chunks. Contrast: «Продолжение следует» (covered by strip) stops appearing 2026-05-28, proving strip works for covered patterns and these are precisely the uncovered classes only ever caught by the chunk-level low-RMS path (all 117 low-rms-hallucination log entries are chunk-context, zero utt). The proposed per-utterance RMS-gated isHallucination+repetition check plus added strip patterns would change user-visible output for the observed classes.

**Фикс (с поправками верификатора):** Two refinements: (a) a per-utterance mixed-script check with the existing 3+-scripts rule would NOT catch the observed CJK junk — «金融红啊请不吝点赞 订阅…» is CJK+Latin (2 scripts) and a lone CJK utterance is 1 script; instead compare the utterance's dominant script against the meeting's configured/dominant language. (b) Per-utterance RMS slicing is sound as proposed since w.start/w.end are trimmed-chunk-relative and `chunk` is the trimmed buffer, but clamp indices to chunk bounds — engine-reported segment times can slightly overshoot the buffer end.

### 5. [MAJOR] Confidence gate — the only semantic per-utterance defense — is contingent on the Pro worker forwarding segment metrics (ITER-048 C1 still unchecked), its silence branch has never fired, and window-level metric duplication makes it both leak junk and drop real speech in 30s blocks

**Где:** `Services/Transcription/TranscriptionConfidenceGate.swift:51`

**Механизм:** Per AppDelegate.swift:1983 the gate is the only non-regex filter per utterance. Three fragilities: (1) CloudWhisperEngine.swift:268-269 — 'the worker currently omits them' — and specs/iterations/ITER-048-asr-cost-quality.md:16-19 (unchecked box): «прокси их сейчас НЕ отдаёт, поэтому confidence gate для Pro-пользователей инертен на cloud-пути … главный анти-галлюцинационный фильтр не работает именно там, где жалуются». If/where the worker drops segments, metrics(for:) returns nil and every utterance is kept. (2) The noSpeechProb silence branch (line 51) is inert on-device (WhisperKit hardcodes 0, per file header) and has ZERO catches in the entire 7-month log — the branch built specifically for invented-speech-over-silence never runs. (3) Whisper assigns window-level avg_logprob/compression_ratio copied onto every segment of a 30s decode window, so the gate judges whole windows: precision-first floor logProbFloor=-1.5 (below Whisper's own -1.0) lets hallucination windows in the -1.0..-1.5 band pass, while the repetition branch (compression>2.4 AND logProb<-0.5) fires on windows of coherent speech.

**Вердикт проверки:** Core defect verified, but the finding's headline leg is wrong. VERIFIED: (a) AppDelegate.swift:1983 gate is the only metric-based per-utterance filter on the meeting path, and DualStreamMerger.swift:24-51 is pure sort+render — gate drops are unrecoverable and gate leaks reach the final transcript; (b) all 20 'repetition' drops in the live suspect-transcripts.log (2026-06-12..2026-08-06) are coherent Russian speech deleted in 3-5-utterance blocks sharing byte-identical window metrics (e.g. 4 texts at compression=2.40/logProb=-0.98, 5 at 2.53/-0.61) — 100% observed false-positive rate, real speech silently missing from user transcripts; (c) silence branch: 0 catches confirmed (log spans ~2 months, not 7 as claimed). REFUTED: the claim that the gate is inert on the Pro cloud path because the worker omits metrics. The deployed metawhisp-api worker (downloaded read-only 2026-08-07) requests verbose_json from Groq and returns `segments: result.segments || []` — raw Groq segment objects that implicitly carry avg_logprob/compression_ratio/no_speech_prob (field names absent from worker source, which is why the stale CloudWhisperEngine.swift:268-269 comment and unchecked ITER-048 C1 box mislead). The client's ProSegment decoder parses them, and the founder's Pro-cloud machine (WhisperKit unloaded per MetaWhisp.log) shows gate drops with real metrics through 2026-08-04 — the gate IS active on the cloud path today.

**Фикс (с поправками верификатора):** Drop the 'ship ITER-048 C1 metric forwarding' part — it is already live (worker passes raw Groq verbose_json segments through; shipping it again is a no-op). The effective fix is client-side in TranscriptionConfidenceGate/AppDelegate: (1) make the repetition branch additionally require ACTUAL text-level repetition on the utterance (TranscriptionCoordinator.containsExcessivePhraseRepetition at TranscriptionCoordinator.swift:711) before dropping — this alone eliminates the observed 100%-false-positive speech loss; (2) window-level metric duplication means threshold tuning cannot fix the -1.0..-1.5 band leak or junk-inside-good-window blindness — add per-utterance TEXT heuristics rather than tightening logProbFloor; (3) housekeeping: correct the stale comment at CloudWhisperEngine.swift:268-269 and mark ITER-048 C1's forwarding sub-item done, so future audits don't re-derive the wrong mechanism.

### 6. [MAJOR] Repetition-loop and boilerplate hallucination filters are disabled for any meeting chunk that contains speech (chunk-level RMS gate)

**Где:** `App/AppDelegate.swift:1925`

**Механизм:** The meeting path runs `isHallucination` (which contains `containsExcessivePhraseRepetition` — the ONLY detector for repeated single words/phrases — plus the boilerplate exact-match list) only when the WHOLE ~5-min chunk's RMS < 0.003 (`if rms < 0.003, TranscriptionCoordinator.isHallucination(text)`). Any chunk with even 10s of real speech has RMS far above 0.003, so these filters never fire on real meetings. But hallucinations happen in the SILENT STRETCHES INSIDE a speech-bearing chunk — a channel is silent for minutes at a time while the other person talks, and `trimSilenceEdges` (line 2077) only strips edges, never mid-chunk silence. Whisper fills those gaps with «Продолжение следует…», «Субтитры сделал», repeated words — and the repetition detector that would catch them is gated off. Remaining defenses are only the narrow regex strip list (finding 3) and the precision-first confidence gate (logProbFloor −1.5, and inert silence-branch on-device, finding 9).

**Вердикт проверки:** Verified end-to-end read-only. (1) AppDelegate.swift:1875 computes RMS over the whole trimmed ~300s chunk and :1925 gates isHallucination behind rms < 0.003; trimSilenceEdges (:2077-2100) guarantees the trimmed chunk starts/ends at RMS>=0.005 windows, so any speech-bearing chunk has RMS far above 0.003 and the gate never opens (chunks under 0.0005 are skipped entirely at :1879, leaving only a 0.0005-0.003 near-silence band). (2) containsExcessivePhraseRepetition (TranscriptionCoordinator.swift:711) is reachable ONLY via isHallucination (:789), and every isHallucination call site codebase-wide is rms<0.003-gated (AppDelegate:1925,:2138; LiveMeetingAdvisor:239; TranscriptionCoordinator:333); the comment at :693-702 confirms it was deliberately moved out of the ungated isAlwaysHallucination. The per-utterance loop (AppDelegate:1976-2003) has NO text-level repetition check. (3) trimSilenceEdges is edges-only, so multi-minute interior silence (the idle channel in dual-pass diarization) stays in the chunk — the classic Whisper repetition-loop trigger. (4) No downstream guard: DualStreamMerger is sort+render only; persistMeetingTranscript (AppDelegate:2164) saves fullText as-is. Two refinements: the boilerplate half is largely mitigated — per-utterance stripHallucinationTokens (:1988) removes «Продолжение следует»/«Субтитры сделал»/DimaTorzok etc., leaving only exact-match-only patterns like «музыка»/"music" uncovered; and the per-utterance confidence gate (TranscriptionConfidenceGate.swift:56, compression>2.4 AND logProb<-0.5, metrics populated by both WhisperKit and CloudWhisperEngine) partially covers within-segment loops — but misses confidently-decoded loops (logProb>=-0.5) and cross-segment loops (phrase repeated once per short segment), both of which the gated text-level detector would catch. So the repetition-loop class of user-reported garbage does reach the final saved meeting transcript.

**Фикс (с поправками верификатора):** Prefer the finding's first fix variant: compute per-utterance RMS from the chunk samples over [w.start, w.end] (offset by leadOffsetSamples) and run isHallucination/containsExcessivePhraseRepetition on utterances whose own audio is near-silent — this preserves the 2026-05-01 design lesson (repetition check gated by actual audio energy so legitimately repetitive speech like «да да да» with real voice energy isn't dropped). Running containsExcessivePhraseRepetition unconditionally per utterance (second variant) risks re-introducing the exact false-positive class that motivated moving the check behind the RMS gate. Also add a cross-utterance check: the chunk-level joined text can loop one short phrase across many segments where per-segment compression ratio stays low; a chunk-grain repetition scan over silent-utterance spans (or dropping runs of identical consecutive utterance texts) closes that hole. Boilerplate exact-match list needs no move — stripHallucinationTokens already runs per utterance; just extend it with the few patterns only present in isHallucination's exact list (e.g. standalone «музыка»/"music").

## Как получают чистоту лучшие (референс)

Best-in-class products get clean transcripts not from a better Whisper but from a pipeline around (or instead of) it. The consensus stack, in priority order for a WhisperKit + Groq-whisper-large-v3 + Deepgram-BYOK dual-channel macOS app: (1) Silero VAD gating per channel so silence never reaches the decoder — this alone removes the 'Thank you for watching / Субтитры делал DimaTorzok' class of hallucination and cuts Groq per-second billing, and matters most on the mostly-silent system-audio channel; (2) WhisperX-style silence-aligned cut-and-merge chunking (~30 s chunks that start/end on silence) instead of blind windows, which also makes overlap-dedup stitching unnecessary except on the live path; (3) no cross-chunk context carry (condition_on_previous_text=False equivalent — separate context-free Groq requests, no prompt-token carry in WhisperKit), which is the mechanism behind repetition-loop poisoning and confirms the ITER-046 rule that correction dictionaries never belong in initial_prompt; (4) segment gates that are already free — Groq verbose_json returns avg_logprob / no_speech_prob / compression_ratio per segment (drop at <-1.0 / >0.6 / >2.4), WhisperKit exposes the same thresholds in DecodingOptions — plus the temperature-fallback ladder to recover looped segments; (5) a RU+EN ghost-phrase blacklist (seeded from the HF whisper-hallucinations dataset, ~7.9k entries) applied only with audio corroboration; (6) an LLM post-cleanup layer (the superwhisper pattern: separate ASR model + cleanup LLM, dictation-guard prompt, raw transcript kept immutable) — this readability layer is most of the perceived gap vs Otter/Granola and is the correct home for the correction dictionary. Backend-specific: Deepgram Nova-3 with smart_format/numerals/utterances/diarize plus multichannel=true natively solves the mic-vs-system separation in one stereo request; OpenAI's own direction (gpt-4o-transcribe ~90% fewer hallucinations per their noise eval, server-side chunking_strategy auto, keywords array, gpt-4o-transcribe-diarize) and ChatGPT Record mode's architecture (live draft transcription, then a definitive pass over the full uploaded audio + LLM summary canvas) validate a copyable two-pass design: live WhisperKit draft, final cloud re-pass into the archive. The one problem no off-the-shelf pipeline solves is the dual-channel discipline itself: per-channel VAD (kills system-channel silence hallucination), capture-layer AEC via voice-processing I/O (kills no-headphones echo double-transcription at the root rather than via text dedup), and timestamp interleave. Key sources: github.com/openai/whisper discussions #679/#2378/#2420, SYSTRAN/faster-whisper VAD docs and defaults, WhisperX paper (robots.ox.ac.uk/~vgg, Bain 2023), HF transformers chunking PR #20104, argmaxinc/WhisperKit 0.7 VAD chunking release notes, Groq speech-to-text docs (console.groq.com), Deepgram smart-format/filler-words/numerals/multichannel docs (developers.deepgram.com), OpenAI cookbook 'Migrating from Whisper to GPT-Transcribe', OpenAI Help Center 'ChatGPT Record', zenn.dev gpt-4o-transcribe migration report, HF dataset sachaarbonel/whisper-hallucinations, arXiv 2501.11378 (non-speech-induced hallucinations).

### Silero VAD gating before ASR
Run a neural voice-activity detector (Silero VAD v5 — ~2 MB ONNX/CoreML model, sub-millisecond per frame) over the audio first and send ONLY detected speech regions to Whisper. Silence, noise, music, and keyboard clatter never reach the decoder. This is faster-whisper's default (vad_filter=true) with tunables: threshold 0.5, min_speech_duration_ms 250, min_silence_duration_ms 2000, speech_pad_ms 400; timestamps are re-mapped back to the original timeline after transcription.

*Применимость:* Highest-leverage single change for all three backends. Run Silero locally per channel (Apple Silicon handles it trivially). WhisperKit: gate which buffers get enqueued; WhisperKit >=0.7 ships a VAD chunk-and-batch strategy but its built-in energy VAD is cruder than Silero — the reference setup is Silero gating in front of WhisperKit chunking. Groq: trim silent spans before upload — fewer hallucinations AND lower cost (Groq bills per second with a minimum per request; the proxy currently pays to transcribe silence). Deepgram: less critical (Nova barely hallucinates on silence) but still saves BYOK spend. The system-audio channel needs this most — it is silent most of the time.

### VAD cut-and-merge chunking (WhisperX pattern)
Replace blind fixed-30s windows: cut any speech region longer than 30 s at its quietest interior point, then merge short neighboring speech regions until each chunk approaches (never exceeds) 30 s. Every chunk begins and ends on silence (WhisperX, Bain et al. 2023, robots.ox.ac.uk/~vgg).

*Применимость:* Implement once in the recording layer, upstream of all backends. Groq: assemble uploads from silence-aligned chunks (also respects the file-size cap and makes each request context-free). WhisperKit: chunkingStrategy .vad approximates this out of the box; feeding it Silero boundaries makes it exact. Deepgram: unnecessary — send whole files.

### Disable cross-chunk context (condition_on_previous_text=False)
Whisper by default feeds the previous 30 s window's decoded text into the decoder prompt for the next window. Turn that off (or hard-cap the carried context) so each chunk decodes independently.

*Применимость:* WhisperKit: do not carry previous tokens as prefill/prompt between chunks. Groq: not a request parameter, but uploading silence-aligned chunks as separate requests achieves the same isolation for free. This also validates the ITER-046 lesson: a correction dictionary must never be fed as initial_prompt — on near-silent audio Whisper echoes the prompt verbatim into the transcript.

### Segment confidence gating (no_speech_prob / avg_logprob / compression_ratio)
Post-filter every returned segment: drop when no_speech_prob > ~0.6 AND avg_logprob < ~-1.0 (Whisper's own internal thresholds), and drop unconditionally when compression_ratio > 2.4 — text that gzip-compresses that well is the decoder looping.

*Применимость:* Free on the Groq path: whisper-large-v3 verbose_json already returns avg_logprob, no_speech_prob, and compression_ratio per segment — filter in the response handler, zero extra latency or cost. WhisperKit: DecodingOptions exposes noSpeechThreshold / logProbThreshold / compressionRatioThreshold natively — set them rather than accepting raw output. Deepgram: no logprobs, but gate on per-word confidence means per utterance.

### Temperature fallback ladder
Decode at temperature 0; if the result trips the quality gates (compression_ratio > 2.4 or avg_logprob < -1.0), re-decode the same chunk at 0.2, then 0.4, up to 1.0. This is reference-Whisper's built-in retry behavior.

*Применимость:* WhisperKit implements the fallback — verify it is enabled with a sane temperatureFallbackCount rather than pinned to a single temperature. Groq: send temperature 0 and rely on server-side handling; client-side, if a returned segment fails the compression-ratio gate, re-submit just that chunk at 0.2 (cheap: chunks are ~30 s).

### Known-hallucination phrase blacklist (per language)
Maintain an exact/fuzzy blocklist of Whisper's signature ghost phrases — EN: 'Thank you for watching', 'Please subscribe', 'Subtitles by ...'; RU: 'Субтитры делал DimaTorzok', 'Продолжение следует...'. The sachaarbonel/whisper-hallucinations dataset on Hugging Face catalogs ~7,900 documented hallucinations across languages, built from a noise-only corpus — a ready seed list. Drop a matching segment only when corroborated by weak audio evidence (high no_speech_prob, very short speech duration inside the segment, or VAD saying mostly-silence).

*Применимость:* Pure post-processing — one Swift filter shared by the WhisperKit and Groq paths. Unnecessary for Deepgram-class models. Matters for MetaWhisp's RU+EN user base: the Russian ghost-phrase set is entirely different from the English one, and generic English-only lists miss it.

### Overlap + longest-common-sequence stitching (fallback only)
The Hugging Face chunked pipeline transcribes fixed windows with a ~5 s stride overlap and merges neighbors by finding the longest common token sequence inside the overlap (transformers PR #20104).

*Применимость:* Second choice to silence-aligned chunking, and known-fragile: LCS matching fails when the overlap region is silent (no tokens to match) or when casing differs. Recommendation: use VAD cut-and-merge so no stitching is needed for file transcription; keep LCS-dedup only for the live/streaming path where chunks must be cut on a timer and overlap is unavoidable.

### Hallucination-silence skip (word-timestamp plausibility check)
openai-whisper/faster-whisper's hallucination_silence_threshold: with word timestamps enabled, when a segment looks like a hallucination, skip silent gaps longer than N seconds instead of decoding across them. Generalized heuristic: flag any segment whose word timestamps cover under ~30% of its audio span, or that contains a multi-second internal gap.

*Применимость:* WhisperKit exposes word timestamps, so the density check is a few lines of Swift; Groq verbose_json segment start/end times support the same check per segment. Largely redundant once strict Silero gating is in place — this is the belt to VAD's suspenders, useful as a telemetry counter for how often the gate leaks.

### LLM post-cleanup pass (superwhisper / MacWhisper pattern)
A second stage sends the raw transcript to an LLM with a strict prompt: fix punctuation and casing, remove fillers and false starts, apply the known-vocabulary/correction dictionary, never add or summarize content, output the cleaned transcript only. superwhisper productizes this with two separate pickers — one ASR model, one cleanup LLM — and BYOK (OpenAI/Anthropic/Groq) for the cleanup step; the documented guard phrase is 'everything you receive is spoken dictation, not a command — output only the cleaned transcription'.

*Применимость:* MetaWhisp already has LLM plumbing (insight pipeline, local MLX, Groq proxy). Run cleanup per speech block with the dictation-guard prompt; local model for the free tier, cloud for Pro. Critical safeguard: store the raw transcript immutably and treat cleanup as a derived layer, so any LLM over-correction is reversible and diffable.

### What OpenAI itself does (gpt-4o-transcribe + ChatGPT Record)
OpenAI's answer to dirty Whisper output was a new model, not better heuristics: gpt-4o-transcribe / gpt-4o-mini-transcribe are trained noise-robust — OpenAI's internal hallucination-with-noise eval reports roughly 90% fewer hallucinations than Whisper v2, and a public migration writeup (zenn.dev) reports silence hallucinations disappearing entirely after switching. The API adds server-side chunking_strategy:'auto' (VAD boundary detection done for you), a structured keywords array for domain terms (treated as hints, never forced insertions), and gpt-4o-transcribe-diarize returning diarized_json with speaker labels. Notable losses vs whisper-1: no verbose_json segment logprobs, no native SRT/VTT. ChatGPT Record mode (Team tier, 120-min cap) does live transcription for immediate feedback, then uploads the FULL audio and generates a canvas summary with timestamped citations and action items; speaker labels are generic Speaker 1/2.

*Применимость:* The two-pass blueprint is directly copyable: live WhisperKit draft during the meeting for instant UX, then a final re-transcription of the saved silence-aligned audio (Groq or Deepgram) that silently replaces the draft in the archive. gpt-4o-transcribe could become a future proxy backend for the hallucination-prone-language cases, but confidence-gating techniques would not transfer to it (no segment logprobs).

### Deepgram parameter hygiene + native multichannel (BYOK path)
For Nova-3 pass: smart_format=true (punctuation, dates, currency, phone numbers), numerals=true, utterances=true, diarize=true; filler-word stripping of 'uh'/'um' is the default. Critically, Deepgram supports multichannel=true: submit one stereo file and get fully independent per-channel transcripts in a single request. There is also a nova-3 'meeting' model variant tuned for conference-room audio.

*Применимость:* Best structural fit for MetaWhisp's dual-capture design: encode mic as the left channel and system audio as the right channel of one stereo file, set multichannel=true, and receive separate mic/system transcripts with per-channel diarization from one BYOK request — the me-vs-them separation the dual-pass Groq workaround approximates, natively.

### Two-channel discipline: per-channel VAD, echo suppression, timestamp interleave
Treat mic and system audio as fully independent ASR streams end-to-end — separate Silero gating, separate chunking, separate confidence gates — then interleave final utterances by wall-clock timestamp. Prevent the mic re-capturing speaker output (no-headphones case) at the source with Apple's voice-processing I/O (setVoiceProcessingEnabled on the AVAudioEngine input node = built-in AEC), with cross-channel fuzzy-text dedup within a +/-2 s window kept only as a guard metric.

*Применимость:* The one technique no off-the-shelf pipeline provides and MetaWhisp must own: it is pure client architecture. Per-channel Silero costs almost nothing; AEC is a capture-layer flag; timestamp interleave is what makes the merged transcript read as a conversation. Applies identically in front of WhisperKit, Groq, and Deepgram (and becomes trivial on Deepgram via multichannel=true).

### Input normalization (16 kHz mono per channel, gain normalization, no aggressive denoise)
Before VAD+ASR: resample each channel to 16 kHz mono (Whisper's native log-Mel input), apply loudness/gain normalization, and skip heavy spectral noise suppression. Community pre-processing findings (openai/whisper discussion #2378) show gain normalization helps while aggressive denoising distorts speech and can raise WER.

*Применимость:* One gain stage in the AVAudioConverter capture path, shared by all backends. Side benefit for the Groq proxy: 16 kHz mono FLAC/Opus uploads are dramatically smaller, staying under upload caps and cutting transfer time.
