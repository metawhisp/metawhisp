# FEAT-0006: The task tracker agents use {#root}

The owner's direction (2026-11-25): MetaWhisp becomes the task tracker for AI agents. Claude Code and Codex connect
over MCP or a command-line tool and keep each project's tasks and backlog in MetaWhisp; nothing appears by itself.
Decisions T1–T11 (planning session) and D1–D8 (this spec's interview, 2026-11-26) are the source; each section cites
the one it implements. The task model, statuses, archive, command and tool surface follow an established open-source
markdown task tracker (MIT); its mechanics are re-implemented here, its texts are not copied.

Base: branch `claude/fix-task-rules-a790c2` (FEAT-0005, drafts). Not released; release only on the owner's word.

## 0. Invariants (read first) {#invariants}

- **I1. One writer.** Only the running app writes the store. The command-line tool and the MCP server send every
  request to the app over a local socket; when the app is not running they start it quietly (no window) and wait for
  it. No second process opens the SwiftData store (T11).
- **I2. Nothing appears by itself.** A tracker task exists only because an agent or the user made it, or the user
  accepted a draft (FEAT-0005). A project is created only by Claude Code / Codex (named after their folder), or by the
  user, or by MetaChat when the user says outright "create project X" (T4, D7).
- **I3. Drafts are the user's.** Agents never see, create, accept, edit or archive a draft (`status == "staged"`).
- **I4. Archive first.** An agent archives (hidden everywhere, restorable, same column on restore). Delete forever
  works only on an archived task and only after the user said yes in the agent's chat (D6, D6b).
- **I5. Stale-save rule.** Every write is a fetch by id in a new context, changed and saved in one synchronous step
  on the main actor; nothing is written from a copy read before an `await`.
- **I6. Projects agents use are real.** A project the tracker knows (`TrackedProject`) is never pruned, merged away
  or renamed by the automatic project passes. Its name changes only by the user.
- **I7. Free.** No Pro gate on any of it (D8). Nothing is added to the menu-bar popover.
- **I8. No reference name** anywhere in the repo, the binary or the texts the agents read.

## 1. What exists today (confirmed in code, 2026-11-26) {#today}

- A project is a `ProjectAlias` row (canonical name + aliases JSON). Tasks reach a project only through
  `conversationId → Conversation.primaryProject → alias` (`ProjectAggregator.details`). `TaskItem` has no project.
- Task lifecycle: `status` `staged` (draft) / `committed` / `dismissed` + `completed` + `isDismissed`. No "in progress".
- `metawhisp-mcp` (`Sources/MetaWhispMCP/main.swift`): read-only, 4 tools over `mcp-snapshot.json`, written by
  `MCPSnapshotService` when the Settings "MCP Server" toggle is on. Not shipped in the DMG.
- Settings → Integrations: "External LLM access" (three setup-doc buttons whose docs are not bundled) and the "MCP
  Server" toggle.
- Automatic project passes (`ProjectAggregator`): `pruneOrphanAliases` deletes rows with no conversations,
  `mergeAliases` deletes the "loser" of two similar rows, `recanonicalizeAll` renames a row to its most-used variant,
  `listProjects` hides rows with fewer than 2 conversations. Each would break an agent's project (§5.4).
- MetaChat `addTask` writes a task with no project (`ChatToolExecutor`).
- After onboarding the app launches without a window (`AppDelegate`), so a launch by `open -g -j` is quiet.

## 2. Architecture {#architecture}

```
Claude Code / Codex ──stdio MCP──▶ metawhisp-cli mcp start ─┐
terminal / scripts  ──argv──────▶ metawhisp-cli task …     ├─▶ unix socket ▶ MetaWhisp.app ▶ TrackerService ▶ store
MetaChat (in app)   ──────────────────────────────────────────────────────────▶ TrackerService
Tasks window (board / list) ─────────────────────────────────────────────────▶ TrackerService
```

- **MetaWhispTrackerKit** (new SwiftPM library, Foundation only, used by the app and the CLI): wire protocol types,
  the task value types (DTOs), MCP tool schemas, guide texts, CLI argument parsing, the plain-text formatting of
  lists and task views, and the pure rules (§3–§5: status parsing, IDs, ordering, checklist edits, dependency checks,
  name normalization, project-root discovery). Pure → unit-tested.
- **TrackerService** (app, `@MainActor`): the owner of tracker data. Every operation of §6, for every caller (socket,
  Tasks window, MetaChat). Returns DTOs or a typed error.
- **TrackerSocketServer** (app): listens on `~/Library/Application Support/<support folder>/tracker.sock`
  (folder 0700, socket 0600), accepts only peers with the user's uid (`getpeereid`), reads one JSON request line,
  runs it on the main actor through `TrackerService`, writes one JSON response line. Starts early at launch.
- **metawhisp-cli** (replaces `metawhisp-mcp`; shipped in `MetaWhisp.app/Contents/Helpers/`): `mcp start` serves
  MCP over stdio; `task …`, `search`, `instructions`, `project` are the CLI. It resolves the project root (§5.1),
  sends `{op, folder, args}` to the app, and prints the kit's text (or JSON with `--json`).
- **AgentConnector** (app): the Settings buttons Connect / Disconnect for Claude Code and Codex (§8).

Why a socket and not the snapshot file: agents must write (T2), and only the app may write (T11). Why a unix socket:
filesystem permissions plus a uid check keep other users and web pages out; no port, no network.

## 3. Data model {#model}

The tracker's own data lives in a separate store file, `Tracker.store` next to the main store, with its own
versioned schema (`TrackerSchemaV1`). Not new entities in the main store: a new main schema version raises
`MWSchemaVersion`, and `scripts/lib/app-install.sh` then refuses to swap the build in (its rollback could not undo the
migration), and a 1.4.8 rolled back onto a V11 store could not open it. A side store leaves the main store's shape
alone; an older build simply ignores the file. `TaskItem` stays the task and the truth for done / dismissed; the side
record only adds. Writes touch the main row first and the side record second; a crash between leaves a plain task
(no project) or a stale `archivedAt` on a live task, which is only a timestamp — never a wrong column.

### 3.1 `TaskTrackerRecord` {#model.record}

The tracker side of one `TaskItem` (1:1 by `taskId`). A task without a record is a plain task (voice, calls, old).

| field | type | meaning |
|---|---|---|
| `taskId` | UUID | `TaskItem.id` |
| `projectId` | UUID? | `ProjectAlias.id`; nil = no project |
| `key` | String? | `"12"` or `"12.1"`; the ID shown is `TASK-<key>`; set with the project |
| `parentTaskId` | UUID? | parent `TaskItem.id` for a subtask |
| `startedAt` | Date? | In Progress while set and the task is not done |
| `archivedAt` | Date? | archived (the task is also `dismissed`) |
| `ordinal` | Double? | manual order |
| `bodyJSON` | String | `TrackerTaskBody` (kit, Codable, every field optional): description, priority, type, labels, assignees, dependencies (task UUIDs), references, documentation, modifiedFiles, acceptance criteria, definition of done, plan, notes, comments, final summary, createdBy |
| `createdAt`, `updatedAt` | Date | |

The body is one JSON column so later fields (milestones, documents) need no migration.

### 3.2 `TrackedProject` {#model.project}

A project the tracker knows; its existence makes the project real (D1, I6).

| field | type | meaning |
|---|---|---|
| `projectId` | UUID | `ProjectAlias.id` |
| `origin` | String | `agent` / `user` / `chat` |
| `foldersJSON` | String | `[String]` remembered root folders (T10) |
| `createdAt`, `updatedAt` | Date | |

### 3.3 Columns are derived {#model.status}

| column | rule |
|---|---|
| Draft | `status == "staged"` (FEAT-0005; never shown to agents) |
| To Do | a task (`isTask`), not completed, `startedAt == nil` |
| In Progress | a task, not completed, `startedAt != nil` |
| Done | a task, `completed` |
| Archive | the task has a record and is dismissed, by any path (`archivedAt` says when); tasks without a record — dropped drafts, junk — are never listed |

Moves: To Do clears `startedAt` and `completed`; In Progress sets `startedAt` (keeps an earlier one) and clears
`completed`; Done sets `completed`, `completedAt`. Archive sets `status = "dismissed"`, `isDismissed`, `archivedAt`;
restore sets `status = "committed"`, clears both — the column comes back from `completed`/`startedAt`. Every other
reader of `TaskItem` keeps working: an In Progress task is an open committed task; an archived one is dismissed.
Status input is case- and space-insensitive (`todo` = `To Do`); anything else is refused with the valid list.

### 3.4 IDs {#model.ids}

`TASK-<n>` per project: next `n` = highest top-level number among the project's records (archived included) + 1;
subtask `TASK-<n>.<m>` = highest child of that parent + 1. Input ignores case and leading zeros (`task-012` =
`TASK-12`). A task gets its key when it gets its project; moving a task to another project gives it a new key there.

## 4. Order, search, checklists, dependencies {#rules}

- Order: tasks with an ordinal first (ascending), then priority (high, medium, low, none), then ID numerically
  (`TASK-2 < TASK-2.1 < TASK-2.10 < TASK-10`). New task: ordinal = highest in the project + 1000 (none if the project
  has no ordinals and is not empty).
- Search: case- and diacritic-insensitive; every query word must appear in the ID, title or body text (description,
  criteria, plan, notes, comments, labels, modified files); title hits rank above body hits. Archived tasks are
  included and marked.
- Acceptance criteria and definition of done: lists of `{text, checked}`, shown 1-based. Set replaces the list (same
  trimmed text keeps its check state, each old entry used once); add appends; remove, check, uncheck take indexes of
  the resulting list; an index out of range is refused with the available range. One line per criterion.
- Dependencies: task IDs of the same project; unknown → refused with the missing IDs; self → refused; a new cycle →
  refused with the cycle. "Ready" = not done, not archived, every dependency done.
- Parent: an existing task of the same project; a subtask's parent cannot be itself or its own subtask.

## 5. Which project {#project}

### 5.1 The folder (in the CLI) {#project.folder}

Root = the folder the agent works in, normalized: walk up from the working directory to the first `.git`; a `.git`
directory → that folder; a `.git` file pointing into `<repo>/.git/worktrees/…` → `<repo>` (a worktree belongs to its
repository); a `.git` file elsewhere (submodule) → that folder; no `.git` up to the home folder → the working
directory itself. The working directory comes from `--cwd`, then `METAWHISP_CWD`, then the MCP client's first
`file://` root (when the client supports roots; held calls wait for the answer at most 5 s), with
`CLAUDE_PROJECT_DIR` (Claude Code sets it for its MCP servers) taken as given like `--cwd`, then the process directory (measured 2026-11-26: Claude Code starts a server in the session's folder, and
for a worktree session in the main repository's folder — both resolve to the same project).

### 5.2 Folder → project (in the app) {#project.match}

1. A remembered folder equal to the root or one of its parents → that project.
2. Name match on the root's last component against every project's canonical name and aliases, normalized:
   lowercase, no spaces, dashes, underscores or dots (T10). Several → a tracked one first, then an exact canonical
   match before an alias match, then the most recently updated. A tracked project whose remembered folder still
   exists elsewhere is another repository of the same name and is not matched; one whose folders are all gone was
   moved or renamed (C4) and is.
3. No match → reads answer "no project for this folder yet; it is created with the first task"; the first create
   makes a project named after the folder (origin `agent`), "<folder> (<parent folder>)" when that name is taken.
4. A write remembers the folder for the project and makes it tracked (an automatic project becomes real, D1).
- Refused as a project folder: `/`, the home folder, and a folder directly under `/`.

### 5.3 MetaChat (D7) {#project.chat}

`addTask` gains `project`: MetaChat picks one of the user's projects (tracked ones listed to it) from the name and
the context; typed chat may ask with its confirm buttons; voice chooses from context. With no fitting project the
task has none. `createProject(name)` exists only for the user's explicit "create project X": an exact normalized
match uses the existing project without asking; a similar one (same normalized prefix or one edit apart) → MetaChat
asks "create new or add to <existing>?"; otherwise it creates it (origin `chat`).

### 5.4 Coupled project passes {#project.coupled}

- `pruneOrphanAliases`: never deletes a tracked project.
- `mergeAliases`: never merges two tracked projects; a tracked row always survives a merge (it takes the other's
  aliases and conversations keep pointing by alias).
- `recanonicalizeAll`: never renames a tracked project.
- `listProjects`: shows tracked projects whatever their conversation count, with their tracker task counts.
- `details(for:)`: adds the project's tracker tasks.
- `deleteProject` (user): removes the `TrackedProject`; its tasks lose project and key ("No project"), nothing else.

## 6. Operations {#ops}

Wire op names = MCP tool names = CLI verbs. Every op except the guides runs in the app. Agents' tools:

| tool | does | notes |
|---|---|---|
| `get_metawhisp_instructions` | guide text: `overview` (default), `task-creation`, `task-execution`, `task-finalization` | static, in the kit |
| `task_create` | title (1–200) + description, status (To Do default / In Progress / Done), priority, type, labels, assignee, dependencies, references, documentation, modifiedFiles, acceptanceCriteria, definitionOfDoneAdd, parentTaskId, dueDate, ordinal, finalSummary | creates the project on first write (§5.2) |
| `task_list` | status, assignee / unassigned, labels (all must match), search, ready, limit (1–1000) | the project's board, no archive; grouped by column |
| `task_search` | query, status, priority, type, modifiedFiles, limit (1–100) | board + archive (marked) |
| `task_view` | id | full record + dependency graph |
| `task_edit` | id + title, description, status, priority, type, labels, assignee, dependencies, references / add / remove, documentation / add / remove, modifiedFiles, dueDate (null clears), ordinal, planSet / planAppend / planClear, notesSet / notesAppend / notesClear, finalSummary / finalSummaryAppend / finalSummaryClear, commentsAppend + commentAuthor, acceptanceCriteriaSet / Add / Remove / Check / Uncheck, definitionOfDoneAdd / Remove / Check / Uncheck | archived → refused, "restore it first" |
| `task_archive` | id | any column |
| `task_restore` | id | back to its column |
| `task_delete` | id + `userConfirmed: true` | archived only; no subtasks left; removes the links other tasks hold to it (D6b) |
| `search_memories`, `search_conversations`, `recent_conversations` | as today, read live from the store | D3 |

Results: plain text (task line `  [PRIORITY] TASK-n - title (status) (ac: x/y)`, sections per column; task view with
status, priority, labels, assignee, dates, parent, subtasks, dependencies, description, criteria, definition of done,
plan, notes, comments, final summary). Errors: `isError: true` + `{code}` (`VALIDATION_ERROR`, `TASK_NOT_FOUND`,
`NO_PROJECT`, `APP_UNAVAILABLE`, `INTERNAL_ERROR`). CLI: `--json` prints the DTO; errors to stderr, exit 1.

The MCP server also serves the guides as resources (`metawhisp://workflow/overview`, `…/task-creation`,
`…/task-execution`, `…/task-finalization`) and an `initialize` instruction to read the overview first.

## 7. Wire protocol and launch {#wire}

Request line: `{"v":1,"op":"task_create","folder":"/abs/root","client":"Claude Code","args":{…}}`. Response line:
`{"ok":true,"text":"…","data":{…}}` or `{"ok":false,"code":"…","message":"…"}`. One request per connection; 1 MB
cap; 30 s read timeout on the client. The server waits at most 20 s for the main actor; a request refused as busy is
cancelled under a lock before it can start, so "try again" never also runs it. The CLI connects; on "no socket" or "refused" it runs
`open -g -j -b com.metawhisp.app` once and retries every 250 ms for up to 30 s, then fails with `APP_UNAVAILABLE`
("MetaWhisp did not start" / "is not installed" / "is running but does not answer — update it"). A degraded store
(`StoreHealthSignal`) refuses every write.

## 8. Connect Claude Code / Codex (T9, D3) {#connect}

Settings → Integrations: "External LLM access" and the "MCP Server" toggle are removed; `MCPSnapshotService` goes and
an existing `mcp-snapshot.json` is deleted once. In their place two rows, Claude Code and Codex, each with Connect /
Disconnect and a one-line state.

Connect: (1) run the agent's own CLI through a login shell with the usual bin folders added to PATH —
`claude mcp add -s user metawhisp -- <cli> mcp start` / `codex mcp add metawhisp -- <cli> mcp start` (an existing
`metawhisp` entry is removed first); (2) put one block between `<!-- METAWHISP TASKS START -->` and
`<!-- METAWHISP TASKS END -->` (with a version line) into `~/.claude/CLAUDE.md` / `~/.codex/AGENTS.md`: tasks and
backlog of the folder's project go to MetaWhisp through its tools; read the instructions first; archive, never
delete without the user's yes. The block replaces an earlier block in place (never two); an unmatched start marker
leaves the file untouched and reports it. Disconnect: `mcp remove` and strip the block. Agent not found → "Install
Claude Code (or Codex), then press Connect again."

## 9. Tasks window (D2) {#ui}

- A switch Board / List and a project picker (All / No project / each tracked project) at the top; "Suggested"
  drafts stay above (FEAT-0005); an Archive button shows archived tasks with Restore.
- Board: three columns To Do / In Progress / Done; drag a card to move it; a card shows ID (with the project's name in
  All), title, priority, checklist progress, "waiting on" tag.
- List: the same tasks, one list grouped by column; the checkbox moves to Done / back to To Do.
- Click a task → detail sheet: title, column, project, priority, labels, description, criteria (tick), definition of
  done, plan, notes, comments, final summary, references; Archive; Delete forever only for an archived task, with a
  confirmation.
- New task: title + project (defaults to the picker's project).
- `tasksEnabled` gates the automatic drafts only; the Tasks window always shows tasks.

## 9b. Projects and tasks are one (owner, 2026-11-26) {#one}

Grilled and confirmed the same day (P1–P8 in the session's decision notes).

- **One project per task, one rule (P5).** A task's project is its tracker record's project when it has one, else
  the project of the conversation it came from (that conversation's `primaryProject`, by name or alias). Every place
  that shows or counts a task's project reads this one rule (`TrackerService.taskProjects`): the board, the list, the
  Projects cards, a project's page. Before, the board read only the record and Projects only the conversation, so a
  call's task showed "no project" on the board and counted under its project in Projects.
- **Agents see the same tasks (§9b, found live 2026-11-27).** An agent addresses tasks by `TASK-n`, and a call's
  task had no number, so an agent in the project's folder saw none of them. Every agent request now starts by
  numbering the project's tasks that the one rule puts there and the tracker has not numbered (`resolve` →
  `numberUnplacedTasks`): the agent lists, views and edits exactly what the user sees, with the number the board shows.
  Drafts and dropped tasks stay out. A numbered task keeps its project when its conversation is later moved.
- **The projects are the Projects list (P5).** Every project the user has (`ProjectAlias`) is in Projects, and only
  those can be a task's project: the board's picker, "+ add project", New task, MetaChat. No project is hidden as
  "one conversation" any more — since T4 nothing invents a project, so there is no noise to hide.
- **Workspace opens on Projects (P1).** The list of projects ends with an empty card "+ Add project" (P4). A project's
  page: its name, then Tasks (the same board / list as the Tasks tab, that project only; a new task there is in it)
  / Conversations / Memories.
- **Tasks tab (P2)** stays and shows every task with its project. A task without one shows a small "+ add project"
  where the name sits (P3): the user's projects, or a new one. No side rows, no separate inbox.
- **Suggestions without a project (P6)** stay suggestions (drafts, hidden after 7 days unreviewed) and, once added,
  are tasks with "+ add project".
- **No "waiting on" tasks (P7).** Nothing makes a task that someone else owes the user: the extractor keeps only the
  user's own items, MetaChat's `addTask` has no assignee. The open ones a user already has are archived once, at the
  first launch of this build (restorable from Archive).

## 9c. Four additions (owner, 2026-11-27, «Да, все четыре», grilled, «Да, делай») {#four}

- **Q1 Edit in the task window.** Title, due day (and clearing it), priority — `editFromApp`, the same fields an
  agent's `task_edit` writes; a picked date is the user's calendar day, stored as an agent's day.
- **Q2 In Progress is taken by one agent session.** «он должен перетащить её в ин прогресс и тогда зачем её второй
  раз брать?» Each MCP server process is a session (`TrackerRequest.session`); the command line has none and the
  agent's name stands in. The agent that moves a task to In Progress holds it (`body.holder`); another session
  cannot take, move or archive it and is told to pick another task. Released by the user moving it out of In
  Progress, by Done, or by the holder archiving it.
- **Q3 Move history, for agents only.** `body.events` (created in, every column change, to and from Archived; by the
  agent, "user" or "MetaWhisp"; the last 50); `task_view` shows the last 10. Nothing in the app.
- **Q4 Archive a project.** "Archive project" in the page's "…"; it leaves the grid and every project picker and gets
  no new conversations; its tasks stay in Tasks with its name; a card "Archived · N" ends the grid and lists them
  with Restore. A task put in it by the user, or an agent writing in its folder, brings it back (reading does not).
  Stored as `ArchivedProject` in `Tracker.store` — schema V2, a new entity, lightweight stage from V1.

## 10. User stories {#stories}

- **S1.** As a developer in Claude Code inside `~/Code/Acme`, I want "add these three tasks" to land in MetaWhisp's
  project Acme, so my backlog outlives the session. *Accept:* three `TASK-n` in Acme, visible on the board; a second
  session in the same folder lists them.
- **S2.** As that developer, I want the agent to pick up a task, record a plan, and finish it with a summary, so I can
  review the work later. *Accept:* the task moves To Do → In Progress → Done with plan, notes, ticked criteria and a
  final summary; the board shows each move.
- **S3.** As a user whose calls already made a project "Acme", I want the agent's tasks to join it. *Accept:* the
  folder `acme` matches the existing project; its conversations and memories stay; it stops being an auto suggestion.
- **S4.** As a user, I want one Connect click to set Claude Code / Codex up. *Accept:* the agent lists `metawhisp`
  among its MCP servers; its global instructions hold one block; Disconnect removes both.
- **S5.** As a user who quit MetaWhisp, I want the agent's write to still land. *Accept:* the app starts without a
  window, the task is written, the agent gets the answer within 30 s.
- **S6.** As a user, I want nothing deleted by accident. *Accept:* agents archive; delete works only on an archived
  task with `userConfirmed`; the app's own Delete forever asks first.
- **S7.** As a user talking to MetaChat, I want "add a task to Acme: …" to land in Acme, and no new project unless I
  ask for one. *Accept:* §5.3.
- **S8.** As a user, I want my tasks as a board or a plain list. *Accept:* §9.

- **S9.** As a user, I want to open a project and see its tasks the way Tasks shows them, with its conversations and
  memories beside. *Accept:* Workspace opens on Projects; a project's page has Tasks (board / list, that project's
  tasks only, a call's task included) / Conversations / Memories.
- **S10.** As a user, I want every task in a project. *Accept:* a task with no project shows "+ add project"; picking
  a project or making one moves it there; the picker lists exactly the Projects list.
- **S11.** As a user, I want no "waiting on someone" tasks. *Accept:* none are made from calls, dictations or
  MetaChat; the open ones are in Archive after the update.

## 11. Corner cases {#corners}

C1 folder is a worktree → its repository's project. C2 subfolder of a remembered folder → that project. C3 two
projects normalize alike → the rule in §5.2. C4 folder renamed → remembered path no longer matches; name match runs
again. C5 project renamed by the user → the folder link holds. C6 project deleted by the user → tasks go to No
project. C7 app not running → quiet launch; not installed / old version → clear error within 30 s. C8 two agents write
at once → the main actor orders them; keys stay unique. C9 store degraded → writes refused. C10 home folder, `/`, a
top-level folder → no project created. C11 edit, delete or move of a draft → refused. C12 edit of an archived task →
refused with "restore it first". C13 delete of a non-archived task, of a task with subtasks, or without
`userConfirmed` → refused. C14 dependency on a missing task, on itself, or a cycle → refused. C15 multi-line
criterion → refused. C16 unknown status / priority / field → refused with the valid list. C17 CLAUDE.md with an
unmatched start marker → left alone. C18 Connect twice → one MCP entry, one block. C19 a peer with another uid → the
socket refuses. C20 a request over 1 MB or not JSON → refused, the server keeps serving. C21 a task moved to another
project → new key there. C22 an In Progress task ticked done in the app and unticked → To Do. C23 a call's task whose conversation has no project
→ "+ add project". C24 a task with a record and a conversation of another project → the record's project. C25 a
conversation's project named by an alias → its project. C26 a project deleted → its tasks show "+ add project". C27
the waiting-on archive runs once; a restored one stays restored.

## 12. Iterations {#iterations}

Each: failing tests first, green, `bash scripts/regression.sh` only on the owner's word (filtered non-screen suites
otherwise), commit, `PROGRESS.md`.

- **I1 Model + kit.** Kit target; DTOs; status / ID / order / checklist / dependency / normalization / root rules;
  text formatting; `TaskTrackerRecord`, `TrackedProject` in `Tracker.store` (own schema, on-disk test).
- **I2 TrackerService.** All ops on the store (on-disk, two contexts); project match / create / remember; §5.4 passes.
- **I3 Socket + CLI + MCP.** Server with uid check; client with launch-and-wait; `mcp start` (initialize, tools,
  resources, roots); CLI verbs; guide texts.
- **I4 Connect.** Registration + instruction block (pure insert / strip tested); Settings rows; snapshot removal;
  `build.sh` ships and signs the CLI.
- **I5 Tasks window.** Board, list, detail, archive, new task, project picker; Projects shows tracked projects.
- **I6 MetaChat.** `addTask(project)`, `createProject` with the similarity question.
- **I7 Done.** Gate on the owner's word, independent review, test build for the owner.

## 13. Not in this spec {#later}
