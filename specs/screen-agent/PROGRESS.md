## Baseline facts

- Screen Agent remains opt-in because `screenContextEnabled` is false by default.
- Current proactive output can be a six-second popup with no continuation.
- Current capture is app/raw-title-change gated and can miss stable-title content changes.
- Existing task and insight systems are independent producers; no shared visit or final decision authority exists.
- Existing MetaChat tool confirmation/undo is the action runtime to reuse.
- Existing `ITER-062` work and all dirty-worktree changes are user-owned and out of scope.

## Known product decisions

- One MetaWhisp identity; Screen Agent capability; MetaChat conversation; Inbox persistence.
- Empty allowlist is fail-closed.
- No persisted screenshots by default.
- One visit/generation, one director, one delivery authority.
- Evidence and silence are enforced in code.
- Screen-derived tasks require confirmation.
- External computer control is not part of this program.
- Default-on is a measured owner decision after dogfood, never an implementation default.

**Случай.** 2 сентября, 18:32–19:59, 87 минут. На 24-й секунде сменилось

решается один раз, при старте. Финализация: `micOff=374400` семплов = ровно 23 с
до смены устройства. Требование владельца: «всегда должно получаться».

**Конструкция (итог 22 раундов независимого ревью — первые десять от Codex,
дальше отдельные агенты, когда у Codex кончился лимит; почти каждая находка
шла от одного корня: учёт таймлайна опросом раз в секунду поверх буфера, куда
пишут после. Раунды v15–v22 ниже переписали часть решений — здесь итоговое
состояние, а не первая версия).**
- *Буфер микрофона держит таймлайн встречи по построению, и размещает его
  сам тап.* Внутри привязки каждый буфер ложится по сэмпл-часам устройства,
  считая от ИСТОКА привязки (`MicRecovery.DevicePlacement`: `origin + round((t −
  originSampleTime) × ratio)`), а не от предыдущего буфера — иначе ошибка
  округления копится (на 24 кГц/1024 это дыра 0.35 с каждые 12 минут).
  Ожидание по устройству ограничено хост-часами за тот же интервал с запасом
  0.25 с + бюджет дрейфа 200 ppm × возраст привязки; скачок сэмпл-времени
  ограничивается ОДИН раз, привязка ре-ориджинится там, где буфер реально лёг.
  Между привязками расстояние меряет `SuspendingClock` захвата. Если между
  последним размещённым семплом и этим буфером зияет больше допуска, ровно эта
  тишина ложится ПЕРЕД ним. Порядок
  верен по построению, «устоявшуюся задержку» учить не нужно вовсе, ничего не
  вставляется при стопе. Допуск на дрожание 0.25 с плюс гистерезис 0.1 с:
  опоздавший на миллисекунды буфер — не дыра и не щелчок. Тик дописывает тишину
  только пока буферы не приходят вообще (память растёт ровно, а не одним куском).
- *Учёт — защёлки в сервисе, снимаемые тиком:* секунды размещённой тишины
  (точная длина пропавшего микрофона) и «детектор сработал с прошлого тика»
  (нулевая серия может начаться и кончиться между опросами). Размещённая
  тишина ≥1 с без открытого простоя — тоже простой, считается и показывается.
- *Успех = здоровая СКОРОСТЬ производства два тика подряд* (≥0.5 с
  сконвертированных семплов на каждую секунду ОКНА, которое тик покрывает),
  а не «вернулся `engine.start()`»
  (раунд 1), не «буфер пришёл и прошло 1.5 с» (раунд 3) и не «накоплено ≥1.5 с
  когда-то» (раунд 5). Капающее устройство не подтверждается никогда, а вне
  простоя открывается как «stream degraded» после трёх тиков низкой скорости.

  которого живого шум пола есть всегда (нули внешнего входа неоднозначны).
- *Решение тика — чистая функция* `MicRecoveryPolicy.decide(MicTickInput)`, и
  сценарии всех раундов — тесты, которые гоняют автомат, а не хелперы вокруг.
- *Эпизод хранит счёт попыток до подтверждения*; после трёх промахов —
  встроенный микрофон по имени (`kAudioDeviceTransportTypeBuiltIn`); когда сам
  встроенный реально привязался и провалил три попытки — пауза до 30 с, но

**Раунд 13 (Codex упёрся в лимит аккаунта; независимый ревьюер-агент).**
Два P1: перенос потери лёг патчем в `stop()`, а не в тик (первое вхождение
якоря оказалось в другой функции) — теперь потребляется тиком, эпизод при
открытии её покрывает; и `.dead` для внешних входов: гарнитура или виртуальный
микрофон с подавлением тишины перезапускались бы прямо на старте, если человек
11 секунд слушает, и уезжали бы на встроенный — `.dead` теперь только для
встроенного транспорта, у которого шум пола есть всегда; мёртвый внешний
доходит до пользователя через `micChannelWasSilent` при стопе. Принятые P2:
размещение внутри привязки — по сэмпл-часам устройства (`AVAudioTime.sampleTime`),
не по времени доставки: поток тапа под нагрузкой опаздывает на сотни
миллисекунд, и это вклинивалось бы нулями в речь; дрейф часов CPU против
устройства тоже уходит. Минимальная пауза между попытками — 5 с (Bluetooth
отдаёт первый буфер через 2–3 с; иначе три «промаха» и переезд на встроенный).
Микрофон, не произведший ничего за запись (нет устройства / разрешения), держит
пустой буфер, как раньше, а брошенные попытки замедляются до 30 с. Порог
карточки — 3 с (или ≥1 с, если не вернулся к концу). `MicRecoveryTests` — в
критических сюитах гейта.

**Раунд 14 (независимый ревьюер), принято.** P1: в ветке сэмпл-часов я прощал
допуск хоста при каждой дыре и якорил индекс на 0.25 с раньше, чем говорят
часы устройства — сдвиг копился (у «моргающего» входа — 5 с/мин). Теперь под
часами устройства заполняется весь дефицит, якорь — по часам устройства
(`max(expected, count)`): пропуск, слишком малый для заполнения, переносится, а
не прощается. P2: движок, переиспользованный между записями и бросивший
`start()`, теперь выбрасывается в могилу (иначе каждая попытка била в тот же
протухший движок); микрофон, не давший ни семпла за встречу, получает карточку
поверх порога («No mic input for this whole meeting»); диктовка якорит
таймлайн на первом буфере (иначе Bluetooth-линк добавлял секунды нулей в
начало каждой диктовки); хвост при стопе — не простой сам по себе (дрейф часов
хоста против устройства делал здоровый микрофон «упавшим к концу»), учёт
снимается до заполнения хвоста; исходы финализации привязаны к поколению
ЖИВОЙ записи, а не к неудавшемуся следующему старту.

**«Нули после аудио» — отклонено в раунде 5, принято частично в раунде 6.**
Для внешних устройств моё возражение стоит: гарнитура с подавлением тишины
отдаёт точные нули минутами, пока владелец слушает; считать это простоем —
перезапускать здоровое устройство и после трёх попыток молча пересадить
человека на встроенный микрофон. Ревью опровергло это для ОДНОГО случая, и
опровержение верное: у живого встроенного микрофона всегда есть шум пола
(это утверждает сам `DeadMicDetector`), поэтому точные нули от него после
аудио — мёртвый поток. Транспорт привязанного устройства читается при
привязке (`boundInputIsBuiltIn`); `.dead` = детектор сработал И (аудио не было
ИЛИ привязан встроенный).

Проверил сам: `DeadMicDetector.tripped` — липкий до `reset()`, поэтому для
встроенного правило спрашивает `isDeadNow` (сработал И нулевая серия ещё
идёт): громкость входа на нуле — серия без конца, мёртв честно; серия, которая
кончилась, — не поломка. Когда сам встроенный микрофон провалил три попытки,
пауза между попытками растёт до 30 с — другого устройства нет, но переткнуть
кабель или поднять громкость можно; сдаваться по-прежнему нельзя.

**Раунд 8, принято.** Заполнение тишиной больше не зависит от «что-то пришло
недавно» (буфер раз в 0.9 с держал дыру открытой навсегда): заполняется любой
дефицит сверх задержки + допуск на дрожание 0.25 с, до края допуска — здоровый
поток не трогается, капающий, заблокированная привязка и остановившийся поток
догоняют часы; на тике, который произвёл здоровую скорость, не заполняется
ничего — остаток дефицита там прогрев и дрожание, и тишина легла бы между
живыми буферами. `DeadMicDetector.tripped` очищается звуком: вторая нулевая серия
внутри одной привязки снова срабатывает (раньше — невидима). Окна паузы
диктовки — на тех же часах, что и буфер (сон между паузой и возобновлением
заглушал всё после пробуждения). `stop()` всегда дозаполняет хвост; хвост ≥1 с
считается простоем и попадает в карточку. «Вернулся» = здоровая скорость хотя бы
один тик, не «что-то капнуло». Замедление до 30 с считает только попытки,
реально привязавшие встроенный микрофон. Эвристика меню-бара: «permission» /
«denied» / 🎤 — не голое слово «microphone»; сообщения о мёртвом потоке и о
тишине больше не носят 🎤.

**Раунд 7, принято.** Часы — `SuspendingClock`, не `ContinuousClock`: сон
машины не «пропавший микрофон» (после ночи это были бы часы нулей и OOM), а
системный канал во сне тоже ничего не пишет — оба канала на часах, которые
спят с машиной. Задержка меряется только на тиках со здоровой скоростью после
подтверждения — капающее устройство превращало дефицит в «нормальную задержку».
Вердикт при стопе: «производит сейчас» = `.delivering` и недавно произвёл (нули
мёртвого устройства и только что снесённый движок — не производят); отозванное
разрешение открывает простой и при стопе. Длительность «мёртвого» встроенного
после аудио — от последнего ненулевого буфера, а не от первого буфера
привязки (иначе полчаса здоровой речи считались бы потерянными); конец простоя
— когда скорость стала здоровой, а не тик подтверждения. Сниф тишины оставляет
запись, только если простой БЫЛ (или есть) и разрешение есть — микрофон без
разрешения проходной не получает. Заметка в меню-баре — без слова
«microphone»: эвристика меню открывает по нему настройки приватности.

**Раунд 6, остальное принято.** Часы — `ContinuousClock` для свежести,
таймлайна и расписания (откат wall-clock делал остановленный поток
«производящим»); отсчёт задержки между попытками — после возврата привязки, а
не до неё; `stop()` судит живой поток, а не кэшированный эпизод; 60-секундный
«сниф тишины» не выбрасывает запись, пока микрофон в восстановлении; заметка о
простое липкая — поздние ошибки финализации присоединяются к ней, не затирают.

**Принято как документация.** Дрейф аудио-часов относительно
wall-clock (~0.36 с/ч при 0.01%) не корректируется — выравнивание честно «с
точностью до дрейфа». Первое высказывание после восстановления может лечь на
≤1 тик раньше. Гарнитура с подавлением тишины, выдающая нули >1 с сразу после
переподключения, неотличима от мёртвой — после трёх попыток уедет на встроенный
микрофон; задокументировано.

**Не проверено живьём.** Ни одной реальной смены устройства на этой сборке.
Проверка: во время тестовой встречи подключить/отключить наушники; в логе
ожидать `mic down (input engine down)` → `attempt 1 bound` → `mic back after …`;
в конце `Stopped: mic=N samples (M produced by the tap …)` с N ≈ длительности.

### Раунд v15 → v16 (2026-09-03)

**v15 нашёл (независимое ревью):**
- P1 — размещение буфера по часам устройства считалось от ПРЕДЫДУЩЕГО буфера с округлением на каждом шаге + односторонний якорь `max(expected, samples.count)`. На 24 кГц/1024 шаг = 682.667 семпла таймлайна → округлялся до 683 на каждом буфере, часы устройства «обгоняли» конвертер на ⅓ семпла за буфер, и каждые ~12 минут сфабрикованный дефицит заливался 350-мс дырой посреди слова. - P2 — мёртвый код, порождённый изменением: `micLagSettleSeconds`, `secondsSinceFirstBuffer`, `timelineElapsed`, `lastBufferAt`, `interruptedAt`.

**Что сделано в v16:**
- Размещение — от НАЧАЛА привязки: `bindOriginIndex`/`bindOriginSampleTime` ставятся на первом буфере привязки (после host-clock заливки), `expected = originIndex + round((t − originSampleTime) × ratio)`. Ошибка округления ≤ ½ семпла на всю жизнь привязки; маленький пропуск переносится точно; якорь `max()` не нужен. `MicRecovery.expectedIndex(originIndex:originSampleTime:sampleTime:inputRate:sampleRate:)`.
- Тест `testAHealthyStreamNeverFillsUnderTheDeviceClockAtAwkwardRates`: 90 минут на 24k/1024, 44.1k/1024, 48k/512, 96k/1024, 48k/1024 с конвертером, выдающим floor(want + фаза) — ноль заливок, таймлайн в пределах 2 семплов от часов устройства.
- Mac без устройства: перед `mic.restart()` — пробник `AudioInputCatalog.availableInputDevices().isEmpty` (чтение свойства, без движка). Пробник считается built-in попыткой → расписание замедляется до 30 с; это и есть выход: появился микрофон — следующий пробник его привязывает. - Sniff: outage оправдывает всё-тихую авто-запись только если микрофон ХОТЬ ЧТО-ТО выдал в этой записи (`micProducedThisRecording`). Микрофон, которого не было, — не outage.
- `Capture.micUnavailable {noPermission, noInputDevice}` при 0 семплов с тапа: `.noInputDevice` → только лог; `.noPermission` → заметка «Microphone permission is off…» (слово permission ведёт клик в Privacy); иначе — как раньше.
- Мёртвые поля удалены (у `interruptedAt`/`lastBufferAt` не было ни одного читателя вне сервиса).

### Раунд v17 → v18 (2026-09-03)

Тест `testDriftIsNotPunishedWhenARealGapArrives`: 3 ч при +100 ppm + дыра 1 с → 16 000 семплов заливки; скачок на 8 ч в том же возрасте — < 4 с.

Плюс: правило «`.delivering` не заливается по host-часам» перенесено из recorder в политику (владелец), два теста скорректированы; устаревшие комментарии про `lastBufferAt`/`confirmSeconds` исправлены.

### Раунд v18 → v19 (2026-09-03)

**v18 подтвердил все семь пунктов v18, прошёл оба сценария** (MacBook: гарнитура вынута на 10-й минуте, вставлена на 12-й → `mic down` → `attempt 1 bound (built-in)` → `mic back after ~3s`; карточка «dropped 2 times for 7s and was brought back», таймлайн в пределах 0.25 с. Mac mini: USB-микрофон вынут навсегда → `no input device — probing every 30 s`; карточка «down once for 50 min and had not come back»). Нашёл:
- **P1 (моя регрессия из v18):** relay компоновал сброс с `finalizationNote`, а заметка чистилась только в `start()` после асинхронных ожиданий → «your side is missing» прошлой встречи висело в поповере всю следующую встречу. **Сделано:** `forgetOutcome()` (заметка + ошибка, синхронно) первым делом в `start()`; поздняя очистка удалена.
